Phase Goal
Phase 4 prevents Fareharbor-style fires at the task level — silence on a single task escalates. Phase 5 prevents them at the project level — multi-step initiatives get planned, tracked structurally, and watched for systemic risk before any single task is even due.
A project is a coherent multi-step effort with milestones, owners, dependencies, and a target completion. The Fareharbor migration would have been a project. The Dallas grand opening is a project. A new SOP rollout is a project. The agent's job is to detect when something is a project, propose the structure, and then track it as one — so that even if individual tasks haven't yet missed deadlines, the agent can spot "this initiative is at risk" and surface it.
This is also where the agent starts to feel like a real Chief of Staff rather than just a task router. Project-level thinking is a different mode of operation.
What you can do at the end of Phase 5:
	•	Brain-dump a multi-step initiative — agent detects it as a project and proposes structure
	•	Approve, edit, or reject the proposed structure
	•	View all active projects in the Projects tab with progress, owners, risk status
	•	Drill into a project to see milestones, dependencies, recent activity, agent observations
	•	Receive proactive risk alerts when a project drifts off-track
	•	Have the daily brief flag projects at risk before any task explicitly fails
What is explicitly NOT in this phase:
	•	No Gantt charts or visual timeline UI (consider in v2)
	•	No external sharing of project views with partners (security/scope concern)
	•	No automated re-planning when a milestone slips (agent surfaces the slip; replan is human decision)
	•	No project templates yet (Phase 6 learning generates these from observed patterns)

1. What Counts as a Project
Not every task should become a project. The overhead of project structure is only worth it for genuinely multi-step efforts.
Heuristics for project detection
During capture, Claude evaluates whether the input describes a project. Triggers:
	•	Three or more distinct sub-asks in one brain-dump
	•	Mention of multiple team members needing to coordinate
	•	A timeline longer than 2 weeks
	•	Words like "migration", "launch", "rollout", "opening", "campaign", "transition"
	•	Reference to dependencies ("after X, then Y", "before we can launch", "once Y is done")
	•	Operational scope ("new location", "new system", "end-to-end")
What stays a single task
	•	Single ask to a single person
	•	Routine operational work
	•	Items completable in under a few days
	•	Items without dependencies
Edge cases
If detection is ambiguous, default to single task. Selmen can promote a task to a project later from the Today tab. Better to under-promote than to spam project structure on routine work.
In the first month of Phase 5 production, expect 3-5 active projects at any time, not 30. The Projects tab is meant to feel curated, not noisy. If it gets noisy, tune detection to be more conservative.

3. Dependency-Aware Dispatch
In Phase 2, every captured task gets dispatched immediately. In Phase 5, tasks tied to a project respect dependencies.
3.1 Dispatch eligibility
A task with project_id and depends_on is dispatched only when ALL tasks in depends_on are 'complete'.
3.2 Sequenced dispatch flow
	•	Project created with 5 milestones (M1, M2, M3, M4, M5)
	•	M1 has no dependencies → dispatched immediately
	•	M2 depends on [M1], M3 depends on [M1], M4 depends on [M2, M3], M5 depends on [M4] → all wait
	•	Team member completes M1, replies 'done', task status → complete
	•	Trigger fires: re-evaluate downstream dependencies
	•	M2 and M3 are now eligible → dispatched (in parallel since no inter-dependency between them)
	•	M4 still waits because both M2 and M3 must complete first
	•	Continue until all milestones complete → project status → complete
3.3 What happens when a milestone slips
	•	Phase 4 chase logic still applies at the milestone level (nudges, escalation)
	•	Phase 5 adds project-level: if a milestone slips significantly, the project's risk_level may auto-elevate
	•	Downstream milestones whose dependencies are slipping get a 'blocked-upstream' indicator
	•	Selmen can manually unblock a downstream milestone ("start it anyway") if priorities shift
3.4 Pseudocode for dependency check
async function checkDispatchEligibility(task) {
  if (!task.depends_on || task.depends_on.length === 0) {
    return { eligible: true };
  }

  const dependencies = await db.select()
    .from(tasks)
    .where(inArray(tasks.id, task.depends_on));

  const allComplete = dependencies.every(d => d.status === 'complete');
  if (allComplete) return { eligible: true };

  const blockers = dependencies.filter(d => d.status !== 'complete');
  return {
    eligible: false,
    blocking: blockers.map(b => ({ id: b.id, title: b.title, status: b.status }))
  };
}

// Called whenever any task transitions to 'complete'
async function onTaskComplete(completedTask) {
  if (!completedTask.project_id) return;

  const downstreamTasks = await db.select()
    .from(tasks)
    .where(and(
      eq(tasks.project_id, completedTask.project_id),
      eq(tasks.status, 'captured')   // only those not yet dispatched
    ));

  for (const t of downstreamTasks) {
    if (t.depends_on?.includes(completedTask.id)) {
      const check = await checkDispatchEligibility(t);
      if (check.eligible) {
        await dispatchTask(t);
      }
    }
  }

  // Also check if project is now complete
  await reevaluateProjectStatus(completedTask.project_id);
}

5. Risk Detection & Project-Level Chase
5.1 Daily project review
Once a day (part of the morning brief job), the agent runs a project review pass over every active project. For each project:
	•	Compute progress: completed milestones / total milestones
	•	Compute pace: progress vs. expected progress at this date
	•	Identify overdue milestones (past due_at, not complete)
	•	Identify blocked milestones (depending on slipping milestones)
	•	Compute current risk_level — auto-elevate if pace is significantly off
	•	Generate observations for the project's agent observations panel
5.2 Risk level auto-adjustment
Risk_level can elevate (or lower) based on observed signals:
From
To
Trigger
normal
elevated
Any milestone overdue OR project pace > 20% behind plan
elevated
critical
Two+ milestones overdue OR escalation raised on a milestone owner OR target_completion will likely miss by >20%
any
low
Project on or ahead of pace AND no recent issues — only auto-lowers from normal, never from elevated/critical (humans recover those)
5.3 Project-level escalation
When risk elevates from normal → elevated, the agent surfaces it to Selmen via:
	•	Today tab Awaiting section: "⚠ Fareharbor Migration moved to elevated risk"
	•	Daily brief: project flagged with reasoning
	•	PWA notification (not SMS unless critical)
When risk elevates to critical:
	•	SMS to Selmen with summary and recommended action
	•	Top of Today tab
	•	Daily brief headline
5.4 Recommended actions for risky projects
The agent doesn't just flag risk — it suggests next steps. Common patterns:
	•	Owner is overloaded (too many other open tasks): suggest reassignment of one milestone
	•	Multiple milestones blocked on same upstream: suggest unblocking that upstream as priority 1
	•	External party silent (broker, lawyer, partner): suggest Selmen places a phone call
	•	Scope expanded mid-project: suggest re-planning to add new milestones explicitly

6. Manual Project Operations
Even with autonomous detection and risk monitoring, Selmen retains full control.
6.1 Create a project manually
From the Projects tab, "+ New Project" opens an empty form. Selmen can either:
	•	Fill it out manually (name, description, target, lead)
	•	Brain-dump into a description field and tap "Plan it for me" — same Claude-Opus planning flow as auto-detection
6.2 Promote a task to a project
From any task in the Today tab, a menu option "Promote to project" opens the planning flow with the task's content as the brain-dump.
6.3 Add a milestone to an existing project
	•	From project detail view, "+ Add milestone" opens an inline form
	•	Set title, description, owner, due date, dependencies on existing milestones
	•	On save, becomes a task linked to the project
6.4 Reorder or re-sequence milestones
	•	Drag-to-reorder in milestone list
	•	Edit dependencies on a per-milestone basis
	•	Saving recomputes the dispatch graph
6.5 Pause a project
	•	Sets status='paused'
	•	Pending milestones not yet dispatched stay un-dispatched
	•	Active milestones (already dispatched) continue normally
	•	Selmen can resume any time
6.6 Cancel a project
	•	Sets status='cancelled'
	•	Soft-cancels all not-yet-complete milestones (they remain in DB but are excluded from views)
	•	Active dispatched messages are not retracted (already sent — can't unsend)
	•	Selmen can choose to send a 'project cancelled' note to all owners (recommended)
6.7 Mark project complete
	•	Sets status='complete'
	•	All non-complete milestones are auto-cancelled
	•	Project archives but stays viewable for reference

7. Tech Decisions for This Phase
Claude usage
	•	Project planning: claude-opus-4-7 — this is the most reasoning-heavy task in the system. Full project plans require careful sequencing and risk identification. Worth the cost.
	•	Project detection during capture: claude-sonnet-4-6 — quick classification, doesn't need deep reasoning
	•	Daily project review: claude-sonnet-4-6 per project; aggregate observations summarized by Opus once a week (Phase 6 pattern)
	•	Volume estimate: Project planning costs ~$1-2 per project. With 3-5 active projects/month, that's $5-10/month total. Daily reviews add ~$5/month.
Dependency graph
depends_on is a JSONB array of task IDs (defined in Document 02 schema). For complex dependency graphs, this is sufficient — Postgres can query containment with @> and JSON operators.
If projects ever exceed 50 milestones with deep nested dependencies (unlikely for Selmen's use case), consider migrating to a dedicated graph schema. For now, JSONB is fine.
Storing milestones snapshot
The projects table has a milestones JSONB column for a lightweight snapshot. This is for fast UI rendering — the project card can show progress without joining tasks. The snapshot is updated whenever any associated task transitions state. Keeps the Projects tab snappy.

9. Background Jobs
9.1 Project review (daily)
Runs as part of the morning brief generation. For each active project, computes progress, pace, risk; updates risk_level if needed; generates observations; updates milestones snapshot.
9.2 Dependency dispatch trigger (event-driven)
Whenever any task transitions to status='complete', a job fires that re-evaluates downstream task eligibility within the same project. Eligible tasks are dispatched per Phase 2 logic.
9.3 Project completion check (event-driven)
Same trigger as above — when a task completes, check if all tasks in the project are now complete. If so, transition project to status='complete'.

13. Risks & Mitigations
Risk: Project detection is too aggressive — every brain-dump becomes a project
Mitigation: Heuristics are conservative. If false-positive rate is high in early use, tighten the prompt. The default of 'when ambiguous, treat as task' protects against noise.
Risk: Project planning suggests bad milestones (wrong owner, unrealistic dates)
Mitigation: Selmen reviews and edits before approval. Override patterns feed Phase 6 learning. Over time, the agent learns Selmen's planning preferences (which team members tend to own which work, typical milestone durations for project types).
Risk: Dependency graph gets out of sync after manual edits
Mitigation: Single source of truth is the depends_on JSONB array on each task. UI edits go through PATCH endpoints that validate (no circular refs). Background job has a daily integrity check that flags any inconsistencies.
Risk: Risk_level oscillates as milestones complete and slip
Mitigation: Hysteresis. Risk only auto-lowers from 'normal' (never from elevated/critical without human action). Once elevated, requires Selmen marking observation as resolved or completing milestones to drop it. This prevents flickering.
Risk: Long-running project becomes a graveyard of stale milestones
Mitigation: Daily review surfaces projects with no activity in 14+ days. Selmen prompted: 'This project hasn't moved. Is it still active or should we archive?' Inactivity is a leading indicator of abandonment.
Risk: Project planning takes too long for Selmen's patience
Mitigation: Opus planning takes 10-30 seconds. PWA shows a progress indicator with cycling status messages. If Selmen is in a hurry, he can skip planning and create the project manually with milestones added later.

14. The Fareharbor Test, Round Two
Phase 4 had a Fareharbor test focused on chase. Phase 5 has its own test focused on project-level prevention.
During staging acceptance, run this:
	•	Brain-dump: "We need to migrate from current booking system to FareHarbor by end of month. Nick handles tracking pixel updates. Orlando handles updating signage and operations training. Tahir handles building the reporting integration. Brandon needs to review the contract first."
	•	Verify the agent detects this as a project and proposes structure with: Brandon's review as M1, Nick's tracking as M2 (depends on M1), Orlando + Tahir as M3 and M4 (depend on M1), final cutover as M5 (depends on all)
	•	Approve the project
	•	Have shadow team progress through M1 (Brandon) and M2 (Nick) normally
	•	Have Test-Tahir's M3 stall — no response to nudges, deadline approaching
	•	Verify: by day 3 of stall, project risk has elevated, downstream M5 shows blocked-upstream, daily brief headlines the issue, recommended action is 'phone call to Tahir + consider parallel start on M5 cutover prep'
If this passes, the project-level Fareharbor protection is working. Multi-step initiatives are now systematically de-risked.
